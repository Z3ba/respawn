# 1. Uvod

## 1.1. Svrha aplikacije

Respawn je mobilna aplikacija za jednu prodavnicu gaming opreme. Objedinjuje pregled tastatura, miševa, slušalica i podloga, poređenje relevantnih karakteristika i planirani tok poručivanja. Korisnik treba da pronađe odgovarajući proizvod, proveri dostupnost i cenu i završi kupovinu uz mali broj razumljivih koraka.

## 1.2. Opseg Kontrolne tačke 1

KT1 obuhvata definisan koncept, korisničke uloge, izabran tehnološki stek, inicijalni projekat, tehničku dokumentaciju i koncept korisničkog interfejsa. Postavljaju se osnove za razvoj; kompletan sistem prodaje nije cilj ove kontrolne tačke.

| Oblast | Stanje u KT1 |
| --- | --- |
| Mobilna aplikacija | Četiri sekcije, navigacija i prazna stanja |
| Lokalna podešavanja | Promena teme i pamćenje izbora |
| Backend | Express osnova i GET /health |
| Modeli | Početni Dart modeli domenskih pojmova |
| Integracije | Firebase i Stripe su planirani |
| Dizajn | Lokalni povezani prototip; Figma status naveden u odeljku 5 |

## 1.3. Ciljevi korisnika

- Pronaći opremu po nazivu, kategoriji, brendu i cenovnom opsegu.
- Pregledati opis, karakteristike, fotografije, cenu i dostupnost proizvoda.
- Sačuvati omiljene proizvode i upravljati korpom nakon prijave.
- Poručiti opremu pouzećem ili karticom u Stripe test režimu i pratiti status porudžbine.

## 1.4. Definicije i skraćenice

UI je korisnički interfejs, a UX iskustvo korišćenja aplikacije. API predstavlja programski interfejs za komunikaciju sistema. CRUD označava kreiranje, čitanje, izmenu i brisanje podataka. Autentikacija proverava identitet korisnika; autorizacija određuje kojim podacima i operacijama korisnik sme da pristupi. Webhook je serversko obaveštenje o događaju kod spoljnog servisa.

# 2. Opis problema i motivacija

## 2.1. Problem koji aplikacija rešava

Pri izboru gaming opreme korisniku su potrebne jasne informacije o karakteristikama koje utiču na njegov način korišćenja: povezanost uređaja, raspored i format tastature, tip prekidača, masa miša i kompatibilnost slušalica. Kada su opis, dostupnost i uslovi kupovine nepregledni, korisnik teže donosi odluku.

Respawn organizuje ponudu kroz kategorije i jedinstven prikaz proizvoda. Planirana pretraga i filteri skraćuju put do odgovarajućeg artikla, dok korpa i pregled porudžbina objedinjuju kupovinu. Prednost koncepta je fokus na jednu prodavnicu sa jednim administratorskim timom.

## 2.2. Ciljna grupa

Primarna ciljna grupa su igrači i korisnici računara koji kupuju periferije za igranje, rad i svakodnevnu upotrebu. Aplikacija treba da bude razumljiva i korisniku koji tek sastavlja svoj prvi setup i korisniku koji traži određene tehničke karakteristike. Sekundarnu grupu čine administratori prodavnice koji održavaju katalog i obrađuju porudžbine.

## 2.3. Tipični scenariji korišćenja

- Gost pregleda kategoriju tastatura i otvara detalje proizvoda pre odluke o registraciji.
- Kupac pronalazi miš, dodaje ga u korpu, unosi adresu i bira način plaćanja.
- Kupac naknadno otvara svoje porudžbine i proverava trenutni status.
- Administrator menja dostupnost proizvoda i ažurira status porudžbine.

# 3. Opis tehnološkog steka

## 3.1. Mobilna aplikacija

Flutter i Dart izabrani su za razvoj aplikacije, sa Androidom kao prvom ciljnom platformom. Flutter omogućava kompoziciju interfejsa kroz widget-e. Material Design koristi se kao osnova, uz sopstvenu grafitno-ljubičastu temu. Web verzija služi kao pomoćni pregled tokom razvoja, a Android build i pokretanje proveravaju se zasebno.

Provider i ChangeNotifier izdvajaju stanje iz ekrana. U KT1 koriste se za temu i učitavanje početnog kataloga. SharedPreferences pamti samo izbor teme. Lokalna podešavanja nisu zamena za proveru korisničkog identiteta ili administratorskih prava.

## 3.2. Podaci i korisnički nalozi - planirano

Firebase Authentication namenjen je registraciji i prijavi putem e-mail adrese i lozinke. Cloud Firestore je planirana baza za korisničke profile, kategorije, proizvode, korpe, omiljene proizvode i porudžbine. Firestore Security Rules i serverske provere ograničavaće pristup prema identitetu i ulozi.

## 3.3. Backend i plaćanje

Node.js i Express čine početnu osnovu HTTP servisa. U KT1 implementiran je samo GET /health. Firebase Admin SDK planiran je za serversku proveru Firebase ID tokena i pouzdane operacije nad podacima.

Stripe je planiran za kartično plaćanje u test režimu. Mobilni deo koristiće paket flutter_stripe i PaymentSheet. Backend će računati iznos iz podataka u bazi, kreirati PaymentIntent i obrađivati verifikovane webhook događaje. Plaćanje pouzećem ostaje paralelna opcija. Kartični brojevi se neće čuvati u Firestore-u ili aplikacionim logovima.

# 4. Planirana arhitektura i inicijalna struktura

## 4.1. Arhitektonski pristup

Mobilni UI komunicira sa provajderima, a provajderi koriste repozitorijume i servise. Repozitorijum predstavlja granicu izvora podataka, tako da prelazak sa početnog praznog kataloga na Firestore ne zahteva mešanje mrežnog koda i prikaza.

**Početni tok u KT1:** ekran -> CatalogProvider -> PendingCatalogRepository -> prazna lista. Tema se čita i čuva kroz ThemeProvider i SharedPreferences.

**Planirani tok:** Flutter -> Firebase Authentication / Firestore, odnosno Flutter -> Express API -> Firebase Admin SDK / Stripe. Privilegovane operacije i potvrda plaćanja izvršavaju se na serveru.

## 4.2. Organizacija projekta

| Celina | Sadržaj i odgovornost |
| --- | --- |
| mobile/lib/core | Vizuelna tema i zajedničke vrednosti |
| mobile/lib/models | Domenski modeli i enumeracije |
| mobile/lib/providers | Stanje kataloga i teme; kasnije korisnika i korpe |
| mobile/lib/repositories | Pristup podacima nezavisan od UI-ja |
| mobile/lib/screens | Ekrani i glavna navigacija |
| mobile/lib/widgets | Ponovo upotrebljive komponente i prazna stanja |
| mobile/lib/services | Pripremljen HTTP klijent sa timeout-om |
| backend/src i backend/test | Express servis, konfiguracija i testovi |
| docs i output/pdf | Izvor dokumentacije, dizajn, provere i PDF |

## 4.3. Korisničke uloge i autorizacija - planirano

Gost je stanje bez prijavljenog naloga. Kupac ima pristup isključivo svojim privatnim podacima, korpi, omiljenim proizvodima i porudžbinama. Administrator upravlja korisnicima i sadržajem prodavnice. Administratorska sekcija nalaziće se u istoj Flutter aplikaciji.

Uloga se ne dodeljuje preko registracione forme i ne određuje se lokalnim prekidačem. Kreiranje administratorskog naloga predstavlja kontrolisanu serversku operaciju. Sakrivanje dugmeta u interfejsu nije dovoljno: svaka zaštićena operacija mora imati proveru pristupa i na sloju podataka ili servera.

# 4. Planirana arhitektura i inicijalna struktura

## 4.4. Osnovni modeli podataka

| Model | Ključni podaci |
| --- | --- |
| AppUser | ID, ime za prikaz, e-mail, uloga kupca ili administratora |
| Category | ID i naziv kategorije |
| Product | ID, kategorija, naziv, opis, cena, zaliha, slika i karakteristike |
| CartItem | ID proizvoda i količina |
| OrderItem | ID i naziv proizvoda, količina i jedinična cena u trenutku kupovine |
| DeliveryAddress | Primalac, telefon, ulica, grad i poštanski broj |
| ShopOrder | ID, kupac, stavke, adresa, ukupan iznos, valuta, način plaćanja, status i vreme |

Novčani iznosi predstavljaju se celim brojevima u najmanjim jedinicama valute, a tekstualni prikaz cene pripada UI sloju. Porudžbina čuva snimak naziva i cene kupljenih stavki. Identitet proizvoda zasniva se na stabilnom ID-ju, nezavisno od promene naziva ili cene.

Predviđene Firestore kolekcije su users, categories, products i orders. Korpa i omiljeno biće vezani za prijavljenog korisnika. Konačna pravila i indeksi baze uvode se zajedno sa funkcionalnom integracijom.

## 4.5. HTTP interfejsi i budući checkout

| Interfejs | Stanje i namena |
| --- | --- |
| GET /health | Implementirano: HTTP 200, status, naziv servisa i verzija |
| Kreiranje checkout-a | Planirano: autorizovan zahtev sa ID-jevima proizvoda, količinama, adresom i načinom plaćanja |
| Stripe webhook | Planirano: verifikacija potpisa i ažuriranje statusa plaćanja |

Tačna JSON specifikacija checkout-a biće definisana pri implementaciji integracije. Klijent ne određuje konačnu cenu. Server proverava proizvode, dostupnost i količine i računa iznos. Za karticu se koristi Stripe test PaymentIntent; rezultat sa klijenta samostalno ne predstavlja dokaz uspešne naplate. Ponovljeni zahtevi i webhook događaji moraju se obrađivati bez dupliranja porudžbine.

## 4.6. Konfiguracija

Početni backend radi na lokalnoj adresi sa podesivim HOST i PORT vrednostima. Primer konfiguracije je u .env.example. Firebase servisni nalog i Stripe tajni ključ neće biti deo mobilne aplikacije ili Git istorije. U KT1 za pokretanje zdravstvene provere nisu potrebni spoljni nalozi.

## 5.2. Implementirani početni ekrani

Početna prikazuje naziv aplikacije, poruku dobrodošlice, prečice za četiri kategorije i prazno stanje ponude. Prečica ili dugme Istraži ponudu vodi na Pretragu. Nazivi kategorija predstavljaju navigacionu strukturu; stvarni proizvodi nisu hardkodovani.

Pretraga omogućava unos i brisanje upita. Pošto još nema povezanog kataloga, rezultat je jasno prazno stanje. Korpa prikazuje da nema stavki i pruža povratak na istraživanje ponude. Profil prikazuje gostujuće stanje i prekidač teme; prijava i registracija još nisu aktivne.

## 5.3. Planirani ekrani kupovine

Katalog će prikazivati proizvode iz baze, dok će detalji sadržati fotografiju, cenu, stanje zalihe i karakteristike. Kupac će moći da sačuva proizvod ili doda odabranu količinu u korpu. Tok kupovine obuhvata prijavu, pregled korpe, podatke za dostavu, izbor pouzeća ili kartice i konačni ishod poručivanja.

# 5. Funkcionalnosti aplikacije i UI/UX koncept

## 5.4. Vizuelni identitet

Respawn koristi tamnu grafitnu osnovu, površine u nešto svetlijem tonu i ljubičasti akcenat. Svetli tekst i jasna hijerarhija daju prednost nazivima, karakteristikama i ceni. Zaobljene kartice, dosledna polja i ista osnovna dugmad održavaju prepoznatljiv izgled. Pored podrazumevane tamne teme, početna aplikacija ima i svetlu temu.

| Token | Vrednost i uloga |
| --- | --- |
| Pozadina | #111116 - osnovna površina |
| Kartice | #1D1D25 - izdvojeni sadržaj |
| Akcenat | #BDA4FF - primarne akcije i naglašavanje |
| Primarni tekst | #F4F1FA - naslovi i bitne informacije |
| Sekundarni tekst | #B7B3C5 - pomoćne informacije |
| Raspored | Osnovni korak 8 px; margine 24 px; dodirne mete najmanje 48 px |

## 5.5. Interaktivni prototip

Lokalni prototip u docs/design/index.html predstavlja planirani izgled konačne aplikacije. Uključuje katalog, detalje, prijavu, registraciju, omiljeno, korpu, dostavu, plaćanje, uspeh, neuspeh plaćanja, profil, porudžbine i osnovnu administraciju. Svi primeri proizvoda i iznosa u prototipu su izmišljeni dizajnerski primeri. Prototip ne prikuplja lozinke ili kartice i ne izvršava porudžbine.

Glavni tok: katalog -> detalji -> korpa -> dostava -> izbor plaćanja -> potvrda. Dodatni tok prikazuje neuspešno kartično plaćanje i povratak na ponovni pokušaj. Prototip sadrži prelaz ka planiranom PaymentSheet-u, bez izrade sopstvene forme za broj kartice.

Pojedinačni SVG ekrani predstavljaju početni materijal za uvoz u Figmu. HTML prototip i SVG fajlovi ne predstavljaju automatski objavljen Figma dokument; stvarni status i link navedeni su na kraju dokumenta.
